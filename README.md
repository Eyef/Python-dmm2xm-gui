# dmm2xm — конвертер музыки Doom 2D (DMM) ↔ трекерные модули

**[English](#english)** · Русский

Конвертер музыкального формата **DMM** из DOS-игры **Doom 2D (1996)** в трекерные модули и обратно, с графическим интерфейсом на tkinter.

**Версия 1.2.** Проект начался как переписанная на Python утилита **dmm2xm** (Grom PE и Artem Vasilev, Object Pascal, v1.5.1), которая умела читать только XM и MOD и не учитывала многие особенности этих форматов — из-за этого сложные файлы конвертировались неточно. В ходе доработки были исправлены найденные в оригинале ошибки, добавлена поддержка S3M и IT, а обратное направление (трекерный модуль → DMM) переработано: тайминг по реальному порядку проигрывания, эффекты, память каналов, громкость внутри ноты, разделение на subsongs, подгонка под ограничения игрового движка (см. раздел «Технические подробности»). Вызова старого exe нет: Wine и Pascal не нужны, всё работает на чистом Python.

## Возможности

| Направление | Вход | Выход |
|---|---|---|
| Прямое | `.dmm` из `doom2d.wad` (по имени песни) или отдельный `.dmm` | `.xm` |
| Обратное | `.xm`, `.it`, `.s3m`, `.mod` | `.dmm` + файлы инструментов `.DMI` |

- Пакетная конвертация всех 30 песен из `doom2d.wad` (с готовой таблицей квантований) или целой папки `.dmm`.
- Конвертация одного файла со всеми настройками (квантование, лимит строк, моно, эмуляция SB-бага).
- Обратная конвертация с выбором восьми каналов из модулей шире 8 каналов, тремя режимами громкости внутри ноты, учётом смещения семпла (Oxx/9xx), разделением модулей на subsongs (Bxx/Cxx).
- Автоматическая подгонка инструментов под ограничения игрового движка (частота 2000–65535 Гц), контроль лимитов формата и лимита ресурсов WAD.

## Состав проекта

| Файл | Назначение |

| `dmm2xm_convert.py` | алгоритм конвертации (прямой и обратный); в начале файла и рядом с функциями лежат настройки: лимиты запекания `SHAPED_*`, `EVENT_MIN_STEP`, `OFFSET_MAX_VARIANTS`, `WAD_MAX_LUMPS` и т. п. |
| `dmm2xm_core.py` | структуры данных и низкоуровневые функции: чтение WAD/DMM/DMI, чтение и запись XM, загрузчики MOD/S3M/IT; константа `DMM_REF_TEMPO` |

| `build_exe.bat` | необязательно: сборка `dmm2xm_gui.exe` для Windows с помощью Nuitka |

## Установка и запуск

Конвертер:

```
python3 dmm2xm_gui.py
```

Требуется Python 3 (проверено на 3.11) и tkinter (обычно идёт в комплекте; в Ubuntu/Debian при необходимости: `apt install python3-tk`). Внешние библиотеки для конвертера **не обязательны**. Если установлен `numpy`, он используется для ускорения передискретизации; без него работает чисто python вариант.

## Сборка exe-файла (необязательно, Windows)

Чтобы запускать конвертер без установленного Python, можно собрать `dmm2xm_gui.exe`: положите `build_exe.bat` и `dmm2xm.ico` в одну папку с тремя `.py` файлами и запустите `build_exe.bat`. Скрипт установит [Nuitka](https://nuitka.net/) (если её нет) и соберёт программу в режиме `--standalone` без консольного окна. Для сборки нужен компилятор C (Nuitka сама предложит скачать MinGW, если компилятор не найден). Результат — папка `build\dmm2xm_gui.dist` с `dmm2xm_gui.exe`.

## Интерфейс конвертера: 4 вкладки

Внизу — общий журнал, в который выводятся сообщения конвертации: предупреждения о рассинхронизации нот, потерянных тиках и т. п., а также сообщения обратной конвертации (см. «Сообщения журнала»).

### 1. «Пакетная конвертация (WAD)»

Аналог `conv_wad.bat` из оригинального пакета dmm2xm. Таблица песен и их квантований предзаполнена теми же значениями, что в `conv_wad.bat` (ALLRIGHT=8, BEST=6, GLAD=8, …), но каждое поле можно изменить, можно добавить свою строку и отключить отдельные песни галочкой. Указывается путь к `doom2d.wad` и папка для результатов (по умолчанию — рядом с WAD); есть общие опции `-r` / `-m` / `-b` (см. вкладку 3). Кнопка «Список песен из WAD» выводит в журнал имена всех DMM-песен, найденных в файле. WAD разбирается один раз на весь пакет.

### 2. «Пакетная конвертация (папка .dmm)»

Аналог `conv_dmm.bat`: та же таблица песен и квантований, но берутся уже распакованные из WAD файлы вида `ИмяПесни.dmm` (например, распакованные сторонним инструментом вроде QPak) из указанной папки. Файлы инструментов (`.DMI`) ищутся рядом с `.dmm` или в подпапке `dmi\`.

### 3. «Один файл (DMM/WAD → XM)»

Прямая конвертация одного файла; поля соответствуют ключам командной строки оригинального `dmm2xm.exe`:

| Ключ | Поле | Значение |
|---|---|---|
| `-q` | Квантование | сколько тиков DMM занимает одна строка XM, 1…31 (по умолчанию 4); см. ниже |
| `-r` | Макс. строк на паттерн | 1…1024 (по умолчанию 256); значения больше 256 нестандартны, некоторые плееры будут глючить — выводится предупреждение. Более длинные паттерны DMM режутся на несколько паттернов XM |
| `-o` | Выходной файл | необязательно; по умолчанию — имя песни/файла + `.xm` |
| `-f` | Песня в WAD | имя DMM-лампа в WAD, если входной файл — `.wad` (кириллица поддерживается, WAD хранит имена в кодовой странице 866; имя вводится точно, с учётом регистра, как в списке песен) |
| `-m` | Моно | без панорамирования инструментов |
| `-b` | Эмуляция SB-бага 44 кГц | к finetune всех семплов добавляется 64 (на ½ полутона выше) |

Поиск инструментов (`.DMI`): если входной файл — WAD, сначала ищутся лампы с этим именем внутри WAD, затем файл рядом с входным файлом, затем в папке самой программы, затем в подпапках `dmi` обеих папок.

Инструменты (если их не больше 11 и не включён `-m`) получают разную панораму по таблице оригинальной утилиты (`PAN_SETTING`); при 12 и более инструментах стерео недоступно (предупреждение в журнале). Для стоковых инструментов Doom 2D (`DMI0011`, `DMI0063`, `DMI0018`, … — всего 12 штук) применяются «ручные» исправления петель, как в оригинальной утилите (`SAMPLE_FIXES`). Неиспользуемые каналы удаляются: в XM остаётся столько каналов, сколько реально использовано (минимум 2).

**Как выбрать квантование.** DMM хранит задержки нот в тиках (66 тиков в секунду), XM — в строках. Квантование `Q` — число тиков DMM на строку XM (XM создаётся с tempo 165 и speed = `Q`). Задержки всех нот в песне должны быть кратны `Q`, иначе ноты «съезжают» на сетку. По окончании конвертации журнал пишет «Minimum note delay was N» (минимальная задержка в тиках; `Q` должно быть её делителем) и перечисляет ноты, не попавшие на сетку («Misaligned note at pattern …»). Если такие предупреждения есть — уменьшите `Q`. `Q = 1` всегда точен по времени, но даёт очень длинные паттерны. Значения для стоковых песен уже подобраны в таблице вкладок 1 и 2.

### 4. «Обратно (XM → DMM)»

Обратная конвертация трекерного модуля (`.xm`, `.s3m`, `.it`, `.mod`; формат определяется по содержимому файла, но расширение должно быть одним из четырёх) в DMM + отдельные файлы инструментов `.DMI`. По умолчанию результат (`<имя>.dmm`) создаётся рядом с исходным файлом, `.DMI` — в той же папке, что и результирующий `.dmm`. Кроме путей к файлам, здесь четыре настройки; при запуске в них уже выбраны рекомендуемые значения.

**а) «Для модулей с >8 каналами».** DMM хранит ровно 8 каналов, значит, у модуля с большим числом каналов нужно выбрать 8:

- *первые 8 по номеру* (как в оригинале);
- *8 самых используемых по количеству нот*;
- *8 самых используемых по суммарной громкости нот* (**рекомендуется, выбрано по умолчанию**): канал с редкими, но громкими нотами (бас, соло) не проигрывает каналу с частыми тихими украшениями. В IT каналы, заглушённые в трекере (mute), в выборе не участвуют и не конвертируются.

**б) «Изменение громкости во время ноты» (слайды Axy/Dxy, огибающие IT/XM).** У ноты DMM одна громкость, а в трекерах она меняется по ходу ноты: затухание хай-хета командой A0F, fade-out, огибающие громкости IT и XM (родная огибающая инструмента XM тоже разбирается и учитывается). Три режима:

- *«Как раньше»*: слайды игнорируются, огибающие IT запекаются в дополнительные инструменты (поведение старой версии).
- *«События громкости»* (**рекомендуется, выбрано по умолчанию**): игровой движок умеет менять громкость уже звучащей ноты особым событием «только громкость» (байт ноты `0xFF`; так сделаны плавные затухания в стоковой песне СОЛО). Слайды и огибающие записываются такими событиями прямо в паттерн: новых инструментов и `.DMI`-файлов не появляется, `.dmm` растёт на 4 байта за каждое изменение громкости (в формате не больше 65535 нот на песню).
- *«Запекать слайды и огибающие в инструменты»*: форма затухания рисуется прямо в семпле отдельным инструментом. Для сложных форм это точнее, но каждая такая нота — новый ресурс в WAD. Лимиты запекания: не больше 250 инструментов, не длиннее 24000 сэмплов на ноту, суммарно не больше 1,2 млн сэмплов; сверх лимита нота получает одну усреднённую громкость.

Установка громкости посреди ноты (Cxx на пустой строке, колонка громкости) в режимах «Как раньше» и «События громкости» записывается событием `0xFF`, а при запекании входит в форму запекаемого инструмента.

**в) «Учитывать смещение семпла (Oxx/9xx)»** (выключено по умолчанию). Трекеры умеют начинать семпл с середины (S3M/IT `Oxx`, MOD/XM `9xx`: «нарезка» барабанных лупов), а DMM нет. Для каждой пары «инструмент + смещение» создаётся копия инструмента, PCM которой начинается с нужного места (смещение внутри петли, до петли и за концом семпла учитываются; за концом одноразового семпла нота молчит). Копия — лишний `.DMI`, поэтому на песню создаётся не больше 32 копий (дальше смещение игнорируется, нота играет с начала; об этом пишется в журнал). На тестовых файлах: S3M +3…5 инструментов, MOD/IT около +20…30. Как и режим «Запекать», это точнее по звучанию, но даёт лишние ресурсы для WAD, поэтому по умолчанию выключено.

**г) «Разделить subsongs (Bxx/Cxx)»** (выключено по умолчанию). Модули с переходами позиции (Bxx в XM/MOD) содержат несколько подпесен: интро, луп, скрытые разделы, недостижимые из начала. Разбиение повторяет логику самого OpenMPT (проверено по `openmpt123 --info/--subsong` и длительностям с точностью до 0,1 с): каждый ордер списка воспроизведения попадает ровно в один сабсонг; песня обрывается перед ордером чужой песни, на замкнувшемся лупе (он играется один раз) или в конце таблицы. Пример — `BGM12.XM`: 4 файла 6:05 / 0:22 / 4:10 / 0:09 (простой проход даёт 10:44, как сумма у OpenMPT). Каждый сабсонг — свой `.dmm` с именем `<имя>_subN.dmm` и уже развёрнутым порядком (переходы середины паттерна укорачивают паттерн, прыжок в чужую песню дальше не ведётся); инструменты общие: одинаковые по содержимому `.DMI` переиспользуют один файл, так что упаковка всех частей плюс объединение их DMI в один WAD дублей не стоит. Замкнувшийся луп превращается в точку повтора DMM (байт после 255), песня без лупа — в повтор с собственного начала. Если таблица целиком образует одну песню, имя файла обычное, без суффикса. Без этой галочки весь список конвертируется в один DMM как есть, а скорости берутся из реальных путей проигрывания (см. п. 1 и раздел про Bxx ниже).

## Поддерживаемые форматы и ограничения

**Что читается при обратной конвертации:**

- **XM** — все версии формата: и «современные» (version > 0x0103 — FastTracker II, OpenMPT, MilkyTracker, Schism Tracker и т. п.), и старые (version ≤ 0x0103), у которых другой, более компактный заголовок паттерна, а данные всех сэмплов идут одним блоком после паттернов.
- **MOD** — Amiga MOD (4/6/8/N-канальные варианты: M.K./M!K!/M&K!/N.T., OCTA/OKTA/CD81/WOW!, xCHN, xxCH, xxCN, TDZx, FLTx, EXOx), включая старый 15-инструментный формат без тега.
- **S3M** — Scream Tracker 3: несжатые PCM-сэмплы; Adlib/FM-инструменты и упакованные сэмплы пропускаются как пустые. Используются только включённые PCM-каналы: заглушённые (бит 7 в настройках канала) и Adlib-каналы (16–31) не конвертируются и не занимают одно из восьми мест DMM. Поддержаны команды A, T, C, D/K/L (слайды громкости), SCx, SDx, SEx, Bxx (переход назад в последнем паттерне становится точкой повтора) и флаг «быстрых слайдов громкости» ST3.00 (Dxy тогда двигается и на первом тике строки).
- **IT** — Impulse Tracker, включая сжатые сэмплы IT214/IT215, режим с инструментами (клавиатурная таблица нота→сэмпл разрешается прямо при чтении), огибающие громкости, петли sustain, стерео-сэмплы.
- Сэмплы **ADPCM4** (редкая опция сжатия в некоторых старых MOD/XM) декодируются для 8-битных моно-сэмплов — единственного случая, где её применяли на практике (оригинал тоже поддерживал ADPCM4 только для него).

**Чего нет:**

- **MOD, упакованные ProPacker'ом** (сигнатура `PPxx` в заголовке), не поддерживаются. Это не сокращение функциональности относительно оригинала: `dmm2xm.exe` тоже не умеет их распаковывать и прерывает загрузку на этой сигнатуре. Такие файлы сначала нужно распаковать сторонним инструментом, и только потом конвертировать.
- **В DMM нельзя выразить**, и обратная конвертация игнорирует: портаменто и вибрато (E/F/G/H/U), арпеджио (J), панораму (у ноты DMM нет панорамы), фильтры и pitch-огибающие, NNA, канальную и глобальную громкость (Mxx/Nxx/Vxx/Wxx), петлю паттерна (SBx/E6x). Переходы позиции Bxx (XM/MOD) отслеживаются: скорость/темп каждого паттерна берутся из реальных путей проигрывания, а при включённой галочке «Разделить subsongs» каждый связный кусок становится отдельным `.dmm`.
- **Не реализованы:** номер строки при переходе на следующий паттерн (Cxx/Dxx: следующий паттерн всегда играется с первой строки; сам разрыв строки Cxx порядок не меняет); старшее смещение семпла SAx (IT; обычное Oxx/9xx поддержано настройкой «в» вкладки 4).
- **Громкость DMM** имеет 127 ступеней, громкость XM — 64, поэтому при `dmm → xm → dmm` чётные значения возвращаются на единицу больше (60 → 61). Частота дискретизации инструмента проходит через finetune XM (шаг 1/128 полутона), так что rate может сместиться на 1–2 Гц. Оба эффекта неустранимы без отдельного канала хранения.

**Лимиты формата DMM** (при превышении — понятная ошибка): не больше 65535 нот в песне, 253 записи в списке порядка, 255 паттернов и 255 инструментов. Сэмплы длиннее 65535 отсчётов или с частотой выше 65535 Гц прореживаются.

## Использование из Python

Конвертацию можно вызывать из своих скриптов, GUI для этого не нужен:

```python
from dmm2xm_convert import ForwardOptions, convert_forward, convert_backward

# DMM из WAD -> XM
opts = ForwardOptions()
opts.input_file = "doom2d.wad"
opts.dmm_in_wad_name = "СОЛО"      # для отдельного .dmm не нужно
opts.output_file = "SOLO.xm"
opts.quantization = 8              # -q
# opts.max_rows = 256 (-r), opts.no_stereo = False (-m), opts.emulate_bug = False (-b)
convert_forward(opts)

# XM / IT / S3M / MOD -> DMM + .DMI
convert_backward("song.xm", "out/song.dmm",
                 channel_selection="loudness",   # "first" | "count" | "loudness"
                 volume_slides="events",         # "off" | "events" | "bake"
                 sample_offsets=False,
                 split_subsongs=False)
```

Обе функции принимают `log=` (функция, получающая строки журнала) и при ошибке бросают `ConversionError`. **Значения по умолчанию в коде (`"first"` / `"off"`) совпадают с поведением оригинала, а в интерфейсе по умолчанию выбраны рекомендуемые (`"loudness"` / `"events"`).** `convert_backward` возвращает путь к результату (или список путей при `split_subsongs=True`).

## Упаковка в WAD и лимиты ресурсов

Конвертер создаёт `.dmm` и `.DMI`; упаковка их в WAD делается внешней утилитой `DMM2WAD` (можно найти в исходниках Doom 2d). Либо моей программой Doom 2D Wad Viewer. По исходникам игры, все загруженные WAD-файлы делят один каталог на `MAX_WAD = 2000` записей (лампов); запись с уже существующим именем только заменяет старую, а новое имя занимает слот. Стоковый `doom2d.wad` уже использует 1468 записей (и имена `DMI0001`…`DMI0091`), свободно 532. Песне нужен 1 ламп DMM плюс различные `.DMI` (одинаковые по содержимому `DMM2WAD` склеивает). Поэтому:

- в конце обратной конвертации журнал пишет «WAD budget»: сколько лампов нужно песне и сколько их свободно;
- `.DMI` новых песен нужно упаковывать с номером старта не меньше 92 (`DMM2WAD list.lst out.wad 92`), иначе `DMI0001…` заменят инструменты оригинальных песен;
- игра при загрузке песни держит в памяти все её инструменты сразу (у стоковых песен до 11 инструментов и ~130 КБ), поэтому режим «События громкости» предпочтительнее запекания.

## Технические подробности

Примеры ниже (`BGM12.XM`, `BGM16.XM`, `VOLKI-B2.xm`, `SWAMP2.mod`, `WFDEMO.S3M`) — модули, скачанные из интернета для проверки конвертера; в репозиторий они не входят.

<details>
<summary><b>Исправления и доработки обратной конвертации XM/MOD/S3M/IT → DMM</b> (отличия от <code>dmm2xm.dpr</code>; часть багов есть в оригинале)</summary>

### Время и порядок песни

**1. Состояние speed/tempo берётся из порядка игры, а не хранения.** Оригинал конвертирует паттерны подряд 0..N-1 с протекающим глобальным `NewSpeed/NewTempo` (`dmm2xm.dpr`, строки 839–844), хотя порядок игры (order table) обычно другой: интро/аутро лежат в конце, секции переиспользуются. Паттерн печётся со «скоростью», оставшейся от чужого, ранее лежащего паттерна. Пример — `WFDEMO.S3M`: порядок игры `[0,1,3,2,4,5,7,10,11,6,6,8,9]`, а speed=12 ставят паттерны 8 и 9, играющие ПОСЛЕ 10 и 11. Оригинал в порядке хранения доходит до 10–11 уже с протёкшим speed=12 и печёт их вдвое длиннее: 1024 тика вместо 507 (+7,8 с на паттерн, молча; +16,8 с на всю песню). Здесь конвертер идёт по order table и печёт около 507 тиков (506,88 по формуле из п. 2). Если один паттерн переиспользуется в песне при разной скорости, DMM физически хранит лишь один вариант (один слот на индекс) — остаётся первое вхождение и печатается предупреждение (пример: `SWAMP2.mod`, паттерн 0 при speed 6 и 3); оригинал молчал.

**2. Точная формула тиков строки: `speed*165/tempo`** с переносом дробного остатка (floor + накопитель) вместо `Round(speed*166/tempo)` оригинала (`dmm2xm.dpr:590`). Строка XM длится `speed*2500/tempo` мс, тик DMM принят за 1000/66 мс, отношение равно `speed*165/tempo` (165 = 2,5·66). Округление каждой строки отдельно накапливает ошибку ±0,5 тика на строку. Пример — `SWAMP2.mod` (speed 6, tempo 125: точно 7,92 тика/строку): оригинал печёт 8 на строку, здесь — в среднем 7,92 (253 против 256 тиков на паттерн, −141 тик / −2,1 с на песню). Остаток тика переносится и между паттернами, а не теряется на границе, поэтому длина песни сходится с расчётной в пределах сотых долей секунды (проверено на IT/S3M/MOD). Константа 165 одна на оба направления (`DMM_REF_TEMPO` в `dmm2xm_core.py`): прямая конвертация создаёт XM с tempo 165 и speed = квантование, обратная делит на то же число — иначе `dmm → xm → dmm` сдвигал бы тайминг. XM, сделанные прямой конвертацией старых версий (tempo 166), читаются обратно на 0,6 % короче.

**Тайминг и DOS-движок.** По исходному коду игры (`SOUND.ASM`) DOS-движок делает такт музыки каждые `(sfreq >> 6)` выходных сэмплов, то есть 64,10 тика/с при 11025 Гц (64,0–64,5 при других частотах звука), а не 66. В оригинальном DOS-движке песня идёт примерно на 3 % медленнее, чем при 66 тиках/с (4:38 в трекере → около 4:46 в игре). Если нужно совпадение именно с DOS-движком, поставьте `DMM_REF_TEMPO = 160`.

**3. Эффекты, влияющие на время.**
- *Note cut (SCx):* каждый cut раньше удлинял канал на x тиков, и каналы расходились друг с другом (до трети секунды на паттерн в реальных IT); теперь время сохраняется, а cut с x ≥ speed игнорируется, как в IT.
- *Pattern delay* (SEx в IT/S3M, EEx в XM/MOD) растягивает строку на нужное число повторов.
- *Повторный запуск ноты* (Qxy в S3M/IT, E9x в MOD/XM, Rxy в XM): нота заново «бьётся» каждые y тиков строки, при x ≠ 0 с изменением громкости на каждом ударе (−1/−2/−4/−8/−16, ×2/3, ×1/2, +1..+16, ×3/2, ×2); Q00 повторяет предыдущее значение канала. В DMM это несколько нот подряд, новых инструментов не нужно. Интервал не короче строки (y ≥ speed) игнорируется. В режиме «Запекать» не применяется (нота там уже целиком нарисована в семпле).
- *Команды Axx/Fxx:* A00 в IT/S3M игнорируется (раньше становилась speed 1), слайды темпа T0x/T1x игнорируются (раньше превращались в tempo 32 навсегда). Bxx в последнем паттерне, ведущий назад, становится точкой повтора песни.

**4. Точка повтора песни.** Значение после маркера 255 в списке порядка DMM — индекс в списке порядка (движок: `curseq = seq[i+1]`), а не номер паттерна. Оба направления работают с индексом: прямая конвертация переводит его в позицию порядка XM (учитывая паттерны, разрезанные из-за лимита строк), обратная берёт restart position XM.

### Ноты, инструменты, громкость

**5. Чтение заголовков инструментов XM по размерам из самого файла.** Оригинал (`BeRoXM.pas`, `LoadInstruments`) читал расширенный заголовок как фиксированные 214 байт и заголовки сэмплов как фиксированные 40 байт, игнорируя поля `isize` и sample header size, — на файлах с нестандартными заголовками всё после первого такого инструмента читалось со сдвигом и превращалось в мусор. Здесь границы берутся из файла, с подстраховкой seek на объявленные позиции.

**6. Имена инструментов всегда ≤ 8 символов:** движок при поиске в WAD сравнивает только первые 8 байт имени, остальное молча отбрасывается. Схема: 6 символов из названия + 2-символьный суффикс слота в базе 36 (у оригинала был десятичный — ломался на 100+ инструментах); плюс проверка папки вывода, чтобы `.DMI` разных треков с одинаковым именем не перезаписывали друг друга.

**7. Громкость из volume-колонки XM:** валидный диапазон сырого байта 0x10–0x50 (уровни 0–64). Проверка `<64` (как в dpr) роняла уровни 48–63 обратно в максимум 127; заодно верхний уровень ограничивается числом 127 вместо вылезавших 129.

**8. Громкость и память канала (MOD/S3M/IT/XM).** Нота с номером сэмпла и без явной громкости сбрасывает канал на громкость сэмпла (правило ProTracker/S3M), нота БЕЗ номера сэмпла и без громкости сохраняет текущую громкость канала (а не играет на максимуме). Последний инструмент канала помнится и между паттернами (нота без номера инструмента в начале следующего паттерна не становится тихой). Проверено на `SWAMP2.mod`. Номер инструмента БЕЗ ноты (S3M, MOD) сбрасывает громкость канала на громкость сэмпла, не перезапуская звук: так делают ритмичное «стробирование» (на чётных строках номер инструмента, на нечётных громкость 8). Этот сброс записывается событием громкости (для XM делается при загрузке: громкость по умолчанию плюс перезапуск огибающей; для IT такой сброс пока не разбирается).

**9. Диапазон нот DMM — 0..95** (таблица частот игры из 96 значений; байт `0xFE` — пауза, `0xFF` — событие громкости, а не нота). Ноты вне диапазона сворачиваются на целое число октав, чтобы не читать таблицу за её пределами.

**10. Кодирование как в игровых данных:** длинная нота — нота с delay=0 (=256 тиков) и одна пауза на остаток (оригинал нарезал по 255 и дробил паузы по 256); пустой канал не добивается паузами до конца паттерна.

### Сэмплы и особенности IT

**11.** Петли **sustain** используются (у DMM нет note-off, ноту всегда «держат», поэтому sustain-петля приоритетнее обычной). **Ping-pong** петли разворачиваются в прямые (если развёрнутый сэмпл влезает в 65535 сэмплов, иначе остаётся прямая петля с предупреждением). **Стерео**-сэмплы сводятся в моно. Сэмплы с C5Speed выше 65535 Гц прореживаются (иначе значение переполнялось бы и играло на две октавы ниже). 16-битные данные при уменьшении до 8 бит округляются, а не усекаются. Каналы, заглушённые в трекере, не конвертируются.

**12. Громкость внутри ноты** — режимы вкладки 4 (см. выше). Внутри — траектория громкости звучащей ноты по слайдам Axy/5xy/6xy/EAx/EBx (MOD/XM), Dxy/Kxy/Lxy (S3M/IT), колонкам громкости XM и IT и установкам Cxx посреди ноты.

### Ограничения движка игры

**13.** Движок ограничивает частоту воспроизведения каждой ноты диапазоном **2000..65535 Гц** (rate инструмента × множитель ноты; слишком высокие ноты быстрых сэмплов «слипаются» в одну частоту — тональность пропадает, слышен гул). Перед записью `.DMI` конвертер для каждого инструмента по реально сыгранным нотам подбирает максимальную безопасную частоту и сжимает PCM по времени в том же отношении: высота и длительность не меняются. Малые коэффициенты сжатия делаются линейной интерполяцией, от 2,5 — оконным sinc-фильтром (с подавлением алиасинга). Если диапазон нот одного инструмента слишком широк для одной частоты, в журнал выводится предупреждение (нужны отдельные копии инструмента). Побочный эффект: при `dmm → xm → dmm` у нескольких стоковых инструментов Doom2D (в оригинале их ноты тоже зажимались) `.DMI` получится слегка изменённым; ноты и тайминг при этом не меняются.

**14. Проверки формата:** не больше 65535 нот в песне (слово в заголовке), 253 записей в списке порядка, 255 паттернов и 255 инструментов — при превышении выдаётся понятная ошибка (раньше падало `struct.error` или данные молча обрезались). Сэмплы длиннее 65535 сэмплов прореживаются.

### Тишина на границе паттерна (`VOLKI-B2.xm`: инструмент обрывается ближе к концу паттерна)

По исходникам игры (`SOUND.ASM`, процедура `playblk`) движок обнуляет «звучащий голос» (`irate`) для ВСЕХ 8 каналов КАЖДЫЙ РАЗ при переходе к новому паттерну в списке воспроизведения — даже если для канала в новом паттерне вообще ничего не записано. В XM/IT/S3M/MOD нота, которую ничего не остановило, просто продолжает звучать через границу паттерна; в DMM же она замолкает, если в начале нового паттерна её не «переударить» явно. Если продолжать ноту паузой (`0xFE`) через границу, то в реальном движке получится именно тот обрыв, который слышен в `VOLKI-B2.xm` (паттерн 9→10: инструмент с петлёй, начатый под конец паттерна 9, обрывается на границе, хотя в оригинале продолжает звучать).

**Решение:** для каждого канала конвертер запоминает, какая ЗАЦИКЛЕННАЯ (не одноразовая — её обрыв в конце данных сэмпла ожидаем и так) нота ещё звучит на конец паттерна, и если начало следующего паттерна её не трогает, добавляет туда ту же ноту/инструмент/громкость — явный «переудар», который восстанавливает обнулённый `irate`. Переудар звучит хвостом оригинала, а не повторной атакой: часы огибающей сдвигаются на возраст ноты (RMS-среднее по `[age, age+hold]` в режиме «Как раньше», хвост огибающей в событиях `0xFF` и в запечённом семпле), затухшая в тишину огибающая вообще ничего не переносит. Без этого `BGM12.XM` на границе 33→33 давал бы залп полногромких атак (85 вместо 53–57) там, где в оригинале тихо доигрывают хвосты.

Если один и тот же паттерн встречается в списке несколько раз с разным «хвостом» предшественника (например, `BGM12.XM`: 30, 33, 33 — первая копия 33 доигрывает ноты из 30, вторая уже ничего), копии с разным входным состоянием разводятся по паттернам-дубликатам с новыми номерами (первый дубль оставляет родной индекс, остальные дописываются в конец, список порядка перемаппируется; в журнал идёт «extra pattern slot(s)»). Дубли различаются и по затухшему входному уровню, поэтому тихий старый хвост и свежая нота не делят один слот.

Проверено: в `VOLKI-B2.xm` граница паттернов 9→10 (каналы 4 и 6) даёт правильный «переудар» той же нотой вместо обрыва. Такая же граница без явного повтора нашлась и в СТОКОВЫХ песнях игры (АС, SUPER и другие) — то есть это реальный, ранее неизвестный дефект, затрагивающий и оригинальную музыку Doom2D, а не только сторонние файлы. В журнал выводится «Pattern-boundary continuity: re-triggered N note(s) …».

### Громкость новой ноты в XM без явной команды громкости (`BGM16.XM`: 97 % нот звучали громче, чем надо)

У FastTracker 2 (и у MOD/S3M/IT) новая нота без явной команды громкости (колонка громкости, Cxx) звучит не на максимуме, а на СОБСТВЕННОЙ громкости инструмента из заголовка сэмпла — многие инструменты специально настраивают её ниже максимума, чтобы не проставлять Cxx на каждой ноте. Для XM-файлов это учитывается отдельным проходом после загрузки (громкость по умолчанию инструмента известна только после того, как загружены И паттерны, И инструменты, — в разных версиях формата XM они хранятся в разном порядке). На `BGM16.XM` это затронуло 97 % всех нот (композитор почти везде полагался на громкость по умолчанию). На MOD/S3M/IT и на XM-файлах, где авторы явно проставляли громкость на каждой ноте (как в `VOLKI-B2.xm`), это ничего не меняет.

### Мультисемпловые XM-инструменты (`sample_map`)

XM-инструмент может хранить несколько разных семплов и раскидывать ноты по ним через карту клавиатуры (например, разные удары барабана на разных клавишах одного инструмента), а весь тракт конвертера, как и сам DMM, устроен проще: один инструмент — один семпл. Пример — `BGM12.XM`: инструмент 19 посылает ВСЕ ноты на второй семпл (19 КБ звука, громкость по умолчанию 37), а нулевой у него пустой; инструмент 2 раскидывает ноты между ДВУМЯ семплами (26 нот из 163 на первый, 137 на второй).

Это обрабатывается на этапе загрузки XM (`_expand_xm_multisample_instruments`): если все сыгранные ноты инструмента попадают в один (ненулевой) семпл, он просто переставляется на место нулевого, номер инструмента не меняется (случай инструмента 19); если ноты расходятся по нескольким семплам, первый использованный остаётся под тем же номером, а под каждый следующий заводится новый номер инструмента — как для IT-драм-китов (случай инструмента 2: 137 нот переходят на новый, 23-й инструмент). Обычные односемпловые инструменты (почти все) это не затрагивает. Такое размножение номеров увеличивает счётчик инструментов, поэтому проверка лимита 255 (п. 14) считает уже размноженные слоты.

### Переходы Bxx в середине песни (`BGM12.XM`/`BGM16.XM`: длительности как в OpenMPT)

Bxx отслеживаются везде (а не только как переход назад в последней строке последнего паттерна, задающий точку повтора):

- скорость/темп каждого паттерна берутся из реальных путей проигрывания (симуляция от начала, от каждого адреса перехода и от позиции после прыгающего паттерна — эффект Fxx внутри недостижимого куска не протекает в чужую песню; при конфликте побеждает самый ранний путь, о чём пишется предупреждение);
- галочка «Разделить subsongs» режет таблицу на связные песни по правилам самого OpenMPT: каждый ордер ровно в одной песне, песня обрывается перед чужим ордером, на замкнувшемся лупе (играется один раз) или в конце таблицы.

Проверено по `openmpt123 --info/--subsong`: `BGM12.XM` даёт 4 сабсонга 6:05 / 0:22 / 4:10 / 0:09 против 6:04 / 0:21 / 4:09 / 0:08 у OpenMPT (сумма 10:44 сходится), `BGM16.XM` — 5 сабсонгов с совпадением до 0,1 с. Без галочки весь список конвертируется в один DMM как есть, но уже с правильными скоростями. Остаточное ограничение: байт повтора DMM указывает на одну позицию порядка, поэтому песня без внутреннего лупа зацикливается с собственного начала, а возврат в паттерн с другим «звенящим» состоянием, чем линейный вход, передаётся приближённо.

### Прямая конвертация DMM/WAD → XM

Работает по алгоритму оригинала; изменения продиктованы обратным направлением и исходным кодом игры:

- XM создаётся с tempo 165 (`DMM_REF_TEMPO`) и speed = квантование;
- точка повтора переводится из индекса списка порядка DMM в позицию порядка XM (см. п. 4);
- нота DMM `0xFF` (событие «только громкость», есть, например, в СОЛО) превращается в ячейку XM только с колонкой громкости, а не в ложную ноту;
- громкость DMM 1 не превращается в «стоп» (0x10 в колонке XM).

Проверка «туда и обратно» (`dmm → xm → dmm`) на 30 песнях `doom2d.wad`: с квантованиями из таблицы первой вкладки все ноты попадают на те же тики у 25 из 30 песен. У остальных пяти (БОЖ_МУЗ, ПРОБА, ТИШЬ, ТЫ_ПОБЕД, ВЗБУЧКА) задержки нот не кратны квантованию из таблицы; с квантованием 1 совпадение по времени у всех 30. # dmm2xm — Doom 2D music (DMM) ↔ tracker module converter

**[Русский](#top)** · English

A converter between the **DMM** music format of the DOS game **Doom 2D (1996)** and tracker modules, with a tkinter GUI.

**Version 1.2.** The project began as a Python rewrite of the **dmm2xm** utility (Grom PE and Artem Vasilev, Object Pascal, v1.5.1), which could only read XM and MOD and ignored many peculiarities of those formats, so complex files converted inaccurately. Along the way the bugs found in the original were fixed, S3M and IT support was added, and the backward direction (tracker module → DMM) was reworked: timing by the real play order, effects, channel memory, in-note volume changes, subsong splitting, fitting to the game engine's limits (see "Technical details"). The old exe is not called: no Wine or Pascal is needed, everything runs in pure Python.

## Features

| Direction | Input | Output |
|---|---|---|
| Forward | `.dmm` from `doom2d.wad` (by song name) or a standalone `.dmm` | `.xm` |
| Backward | `.xm`, `.it`, `.s3m`, `.mod` | `.dmm` + `.DMI` instrument files |

- Batch conversion of all 30 songs from `doom2d.wad` (with a ready-made table of quantization values) or of a whole folder of `.dmm` files.
- Single-file conversion with every option (quantization, row limit, mono, SB-bug emulation).
- Backward conversion with selection of 8 channels from modules wider than 8 channels, three in-note volume modes, sample offset support (Oxx/9xx), and splitting modules into subsongs (Bxx/Cxx).
- Automatic fitting of instruments to the game engine's limits (2000–65535 Hz playback rate), checks of the format limits and of the WAD resource limit.

## Converter interface: 4 tabs

A shared log panel at the bottom shows the conversion messages: warnings about misaligned notes, lost ticks, etc., as well as the backward-conversion messages (see "Log messages").

### 1. "Пакетная конвертация (WAD)" — batch conversion from a WAD

Equivalent of `conv_wad.bat` from the original dmm2xm package. The table of songs and their quantization values is pre-filled with exactly the values from `conv_wad.bat` (ALLRIGHT=8, BEST=6, GLAD=8, …), but every field is editable, you can add your own row and disable individual songs with the checkbox. You specify the path to `doom2d.wad` and an output folder (next to the WAD by default); the common `-r` / `-m` / `-b` options are available (see tab 3). The "Список песен из WAD" (list songs from WAD) button prints the names of all DMM songs found in the file to the log. The WAD is parsed once for the whole batch.

### 2. "Пакетная конвертация (папка .dmm)" — batch conversion from a folder

Equivalent of `conv_dmm.bat`: the same table of songs and quantization values, but it takes already extracted `ИмяПесни.dmm` files (for example, extracted from a WAD with a third-party tool such as QPak) from the given folder. Instrument files (`.DMI`) are looked up next to the `.dmm` or in a `dmi\` subfolder.

### 3. "Один файл (DMM/WAD → XM)" — single file

Forward conversion of one file; the fields correspond to the command-line switches of the original `dmm2xm.exe`:

| Switch | Field | Meaning |
|---|---|---|
| `-q` | Quantization | how many DMM ticks one XM row takes, 1…31 (default 4); see below |
| `-r` | Max rows per pattern | 1…1024 (default 256); values above 256 are non-standard and some players will glitch — a warning is printed. Longer DMM patterns are split into several XM patterns |
| `-o` | Output file | optional; defaults to the song/file name + `.xm` |
| `-f` | Song in WAD | name of the DMM lump in the WAD when the input is a `.wad` (Cyrillic is supported, the WAD stores names in code page 866; enter the name exactly, case-sensitive, as shown in the song list) |
| `-m` | Mono | no instrument panning |
| `-b` | Emulate the SB 44 kHz bug | adds 64 to the finetune of every sample (half a semitone up) |

Instrument (`.DMI`) lookup: if the input is a WAD, lumps with that name inside the WAD are searched first, then a file next to the input file, then in the program's own folder, then in the `dmi` subfolders of both.

Instruments (if there are no more than 11 of them and `-m` is off) get different panning from the original utility's table (`PAN_SETTING`); with 12 or more instruments stereo is unavailable (a warning is logged). For stock Doom 2D instruments (`DMI0011`, `DMI0063`, `DMI0018`, … — 12 in total) the hand-made loop fixes of the original utility are applied (`SAMPLE_FIXES`). Unused channels are removed: the XM keeps only as many channels as were actually used (at least 2).

**Choosing the quantization.** DMM stores note delays in ticks (66 ticks per second), XM stores them in rows. The quantization `Q` is the number of DMM ticks per XM row (the XM is created with tempo 165 and speed = `Q`). The delays of all notes in a song must be multiples of `Q`, otherwise notes get snapped to the grid. At the end of a conversion the log prints "Minimum note delay was N" (the minimum delay in ticks; `Q` must be a divisor of it) and lists the notes that missed the grid ("Misaligned note at pattern …"). If there are such warnings, decrease `Q`. `Q = 1` is always exact in time but produces very long patterns. Values for the stock songs are already set in the tables of tabs 1 and 2.

### 4. "Обратно (XM → DMM)" — backward conversion

Backward conversion of a tracker module (`.xm`, `.s3m`, `.it`, `.mod`; the format is detected from the file contents, but the extension must be one of the four) into DMM plus separate `.DMI` instrument files. By default the result (`<name>.dmm`) is written next to the source file, and the `.DMI` files go to the same folder as the resulting `.dmm`. Besides the file paths there are four settings; the recommended values are preselected on startup.

**a) "Для модулей с >8 каналами" (modules with more than 8 channels).** DMM stores exactly 8 channels, so for a module with more channels 8 have to be chosen:

- *first 8 by number* (as in the original);
- *8 most used by note count*;
- *8 most used by total note loudness* (**recommended, selected by default**): a channel with rare but loud notes (bass, solo) does not lose to a channel of frequent quiet embellishments. In IT, channels muted in the tracker are excluded from the selection and are not converted.

**b) "Изменение громкости во время ноты" (volume changes during a note: Axy/Dxy slides, IT/XM envelopes).** A DMM note has a single volume, while in trackers volume changes as the note plays: hi-hat decay with A0F, fade-out, IT and XM volume envelopes (the native XM instrument envelope is also parsed and honoured). Three modes:

- *"Как раньше" (as before)*: slides are ignored and IT envelopes are baked into extra instruments (the original's behaviour).
- *"События громкости" (volume events)* (**recommended, selected by default**): the game engine can change the volume of an already sounding note with a special "volume only" event (note byte `0xFF`; the smooth fades in the stock song СОЛО are made this way). Slides and envelopes are written as such events straight into the pattern: no new instruments or `.DMI` files appear, and the `.dmm` grows by 4 bytes per volume change (the format allows at most 65535 notes per song).
- *"Запекать слайды и огибающие в инструменты" (bake into instruments)*: the fade shape is drawn into the sample as a separate instrument. For complex shapes this is more accurate, but every such note is a new WAD resource. Baking limits: at most 250 instruments, at most 24000 samples per note, at most 1.2 million samples in total; beyond a limit the note gets a single averaged volume.

Setting the volume mid-note (Cxx on an empty row, the volume column) is written as a `0xFF` event in the "as before" and "volume events" modes, and in baking mode it becomes part of the baked instrument's shape.

**c) "Учитывать смещение семпла (Oxx/9xx)" (honour sample offset)** (off by default). Trackers can start a sample from the middle (S3M/IT `Oxx`, MOD/XM `9xx`: "slicing" of drum loops), DMM cannot. For every "instrument + offset" pair a copy of the instrument is created whose PCM starts at the required position (offsets inside the loop, before the loop and past the end of the sample are handled; past the end of a one-shot sample the note is silent). A copy is an extra `.DMI`, so at most 32 copies are created per song (beyond that the offset is ignored and the note plays from the start; this is reported in the log). On the test files: S3M +3…5 instruments, MOD/IT about +20…30. Like the baking mode, this sounds more accurate but costs extra WAD resources, hence it is off by default.

**d) "Разделить subsongs (Bxx/Cxx)" (split subsongs)** (off by default). Modules with position jumps (Bxx in XM/MOD) contain several sub-songs: an intro, a loop, hidden sections unreachable from the start. The split follows OpenMPT's own logic (checked against `openmpt123 --info/--subsong` and durations to within 0.1 s): every order of the play list belongs to exactly one subsong; a song ends before an order that belongs to another song, at a closed loop (it is played once) or at the end of the table. Example — `BGM12.XM`: 4 files of 6:05 / 0:22 / 4:10 / 0:09 (a plain pass gives 10:44, the same as OpenMPT's sum). Every subsong is its own `.dmm` named `<name>_subN.dmm` with the play order already unrolled (mid-pattern jumps shorten the pattern, a jump into another song is not followed); instruments are shared: `.DMI` files with identical contents reuse one file, so packing all parts and merging their DMIs into one WAD costs no duplicates. A closed loop becomes the DMM restart point (the byte after 255); a song without a loop becomes a repeat from its own start. If the whole table forms one song, the file name is plain, without a suffix. Without this checkbox the whole list is converted into one DMM as is, and speeds are taken from the real playback paths (see item 1 and the Bxx section below).

## Supported formats and limitations

**What is read in backward conversion:**

- **XM** — all format versions: both "modern" ones (version > 0x0103 — FastTracker II, OpenMPT, MilkyTracker, Schism Tracker, etc.) and old ones (version ≤ 0x0103), which have a different, more compact pattern header and store all sample data in one block after the patterns.
- **MOD** — Amiga MOD (4/6/8/N-channel variants: M.K./M!K!/M&K!/N.T., OCTA/OKTA/CD81/WOW!, xCHN, xxCH, xxCN, TDZx, FLTx, EXOx), including the old 15-instrument format with no tag.
- **S3M** — Scream Tracker 3: uncompressed PCM samples; Adlib/FM instruments and packed samples are skipped as empty. Only enabled PCM channels are used: muted channels (bit 7 in the channel settings) and Adlib channels (16–31) are not converted and do not take one of the eight DMM slots. Supported commands: A, T, C, D/K/L (volume slides), SCx, SDx, SEx, Bxx (a backward jump in the last pattern becomes the restart point) and the ST3.00 "fast volume slides" flag (Dxy then also moves on the first tick of a row).
- **IT** — Impulse Tracker, including compressed IT214/IT215 samples, instrument mode (the note→sample keyboard table is resolved right at load time), volume envelopes, sustain loops, stereo samples.
- **ADPCM4** samples (a rare compression option in some old MOD/XM files) are decoded for 8-bit mono samples — the only case where it was used in practice (the original also supported ADPCM4 only for that case).

**What is not supported:**

- **MODs packed with ProPacker** (the `PPxx` signature in the header) are not supported. This is not a loss of functionality compared with the original: `dmm2xm.exe` cannot unpack them either and aborts loading when it sees this signature. Such files must first be unpacked with a third-party tool and only then converted.
- **DMM cannot express**, and backward conversion ignores: portamento and vibrato (E/F/G/H/U), arpeggio (J), panning (a DMM note has no panning), filters and pitch envelopes, NNA, channel and global volume (Mxx/Nxx/Vxx/Wxx), pattern loop (SBx/E6x). Position jumps Bxx (XM/MOD) are tracked: the speed/tempo of every pattern is taken from the real playback paths, and with the "split subsongs" checkbox on, every connected piece becomes a separate `.dmm`.
- **Not implemented:** the row number on a jump to the next pattern (Cxx/Dxx: the next pattern is always played from its first row; the Cxx row break itself does not change the order); the high sample offset SAx (IT; the ordinary Oxx/9xx is supported by setting "c" of tab 4).
- **DMM volume** has 127 steps, XM volume has 64, so in `dmm → xm → dmm` even values come back one higher (60 → 61). The instrument's sample rate passes through the XM finetune (1/128 semitone step), so the rate may shift by 1–2 Hz. Both effects are unavoidable without a separate storage channel.

**DMM format limits** (a clear error is raised when exceeded): at most 65535 notes per song, 253 order list entries, 255 patterns and 255 instruments. Samples longer than 65535 frames or with a rate above 65535 Hz are decimated.

## Using it from Python

The conversion can be called from your own scripts; the GUI is not needed:

```python
from dmm2xm_convert import ForwardOptions, convert_forward, convert_backward

# DMM from a WAD -> XM
opts = ForwardOptions()
opts.input_file = "doom2d.wad"
opts.dmm_in_wad_name = "СОЛО"      # not needed for a standalone .dmm
opts.output_file = "SOLO.xm"
opts.quantization = 8              # -q
# opts.max_rows = 256 (-r), opts.no_stereo = False (-m), opts.emulate_bug = False (-b)
convert_forward(opts)

# XM / IT / S3M / MOD -> DMM + .DMI
convert_backward("song.xm", "out/song.dmm",
                 channel_selection="loudness",   # "first" | "count" | "loudness"
                 volume_slides="events",         # "off" | "events" | "bake"
                 sample_offsets=False,
                 split_subsongs=False)
```

Both functions accept `log=` (a function that receives the log strings) and raise `ConversionError` on failure. **The defaults in code (`"first"` / `"off"`) match the original's behaviour, while the GUI preselects the recommended ones (`"loudness"` / `"events"`).** `convert_backward` returns the path of the result (or a list of paths with `split_subsongs=True`).

## Packing into a WAD and resource limits

The converter produces `.dmm` and `.DMI` files; packing them into a WAD is done by the external `DMM2WAD` utility (not part of this project). According to the game's source, all loaded WAD files share one directory of `MAX_WAD = 2000` entries (lumps); an entry with an existing name merely replaces the old one, while a new name takes a slot. The stock `doom2d.wad` already uses 1468 entries (and the names `DMI0001`…`DMI0091`), leaving 532 free. A song needs 1 DMM lump plus its distinct `.DMI` files (`DMM2WAD` merges those with identical contents). Therefore:

- at the end of backward conversion the log prints "WAD budget": how many lumps the song needs and how many are free;
- the `.DMI` files of new songs must be packed with a start number of at least 92 (`DMM2WAD list.lst out.wad 92`), otherwise `DMI0001…` will replace the instruments of the original songs;
- when loading a song the game keeps all of its instruments in memory at once (stock songs have up to 11 instruments and ~130 KB), so the "volume events" mode is preferable to baking.

## Technical details

The examples below (`BGM12.XM`, `BGM16.XM`, `VOLKI-B2.xm`, `SWAMP2.mod`, `WFDEMO.S3M`) are modules downloaded from the internet to test the converter; they are not part of the repository.

<details>
<summary><b>Fixes and improvements in backward conversion XM/MOD/S3M/IT → DMM</b> (differences from <code>dmm2xm.dpr</code>; some of the bugs are present in the original)</summary>

### Timing and song order

**1. Speed/tempo state follows the play order, not the storage order.** The original converts patterns sequentially 0..N-1 with a leaking global `NewSpeed/NewTempo` (`dmm2xm.dpr`, lines 839–844), although the play order (order table) usually differs: intros/outros sit at the end, sections are reused. A pattern is baked with the "speed" left over from some other pattern stored before it. Example — `WFDEMO.S3M`: the play order is `[0,1,3,2,4,5,7,10,11,6,6,8,9]`, and speed=12 is set by patterns 8 and 9, which play AFTER 10 and 11. In storage order the original reaches 10–11 with the leaked speed=12 and bakes them twice as long: 1024 ticks instead of 507 (+7.8 s per pattern, silently; +16.8 s over the whole song). Here the converter walks the order table and bakes about 507 ticks (506.88 by the formula in item 2). If one pattern is reused in a song at different speeds, DMM physically stores only one variant (one slot per index) — the first occurrence is kept and a warning is printed (example: `SWAMP2.mod`, pattern 0 at speed 6 and 3); the original stayed silent.

**2. Exact row tick formula: `speed*165/tempo`** with the fractional remainder carried over (floor + accumulator) instead of the original's `Round(speed*166/tempo)` (`dmm2xm.dpr:590`). An XM row lasts `speed*2500/tempo` ms, a DMM tick is taken as 1000/66 ms, and the ratio is `speed*165/tempo` (165 = 2.5·66). Rounding every row separately accumulates an error of ±0.5 tick per row. Example — `SWAMP2.mod` (speed 6, tempo 125: exactly 7.92 ticks/row): the original bakes 8 per row, here the average is 7.92 (253 vs 256 ticks per pattern, −141 ticks / −2.1 s per song). The tick remainder is also carried between patterns instead of being lost at the boundary, so the song length matches the calculated one to within hundredths of a second (checked on IT/S3M/MOD). The constant 165 is the same for both directions (`DMM_REF_TEMPO` in `dmm2xm_core.py`): forward conversion creates an XM with tempo 165 and speed = quantization, and backward conversion divides by the same number — otherwise `dmm → xm → dmm` would shift the timing. XMs made by forward conversion in older versions (tempo 166) are read back 0.6 % shorter.

**Timing and the DOS engine.** According to the game's source (`SOUND.ASM`), the DOS engine advances the music every `(sfreq >> 6)` output samples, i.e. 64.10 ticks/s at 11025 Hz (64.0–64.5 at other sound rates), not 66. In the original DOS engine a song therefore plays about 3 % slower than at 66 ticks/s (4:38 in the tracker → about 4:46 in the game). If you need a match with the DOS engine specifically, set `DMM_REF_TEMPO = 160`.

**3. Effects that affect timing.**
- *Note cut (SCx):* every cut used to lengthen the channel by x ticks, and channels drifted apart (up to a third of a second per pattern in real IT files); now timing is preserved, and a cut with x ≥ speed is ignored, as in IT.
- *Pattern delay* (SEx in IT/S3M, EEx in XM/MOD) stretches the row by the required number of repeats.
- *Note retrigger* (Qxy in S3M/IT, E9x in MOD/XM, Rxy in XM): the note is struck again every y ticks of the row, with a volume change on every hit when x ≠ 0 (−1/−2/−4/−8/−16, ×2/3, ×1/2, +1..+16, ×3/2, ×2); Q00 repeats the channel's previous value. In DMM this is several notes in a row, no new instruments needed. An interval not shorter than the row (y ≥ speed) is ignored. Not applied in "bake" mode (there the note is already drawn entirely into the sample).
- *Axx/Fxx commands:* A00 in IT/S3M is ignored (it used to become speed 1), tempo slides T0x/T1x are ignored (they used to turn into tempo 32 forever). Bxx in the last pattern, pointing backwards, becomes the song's restart point.

**4. Song restart point.** The value after the 255 marker in the DMM order list is an index into the order list (engine: `curseq = seq[i+1]`), not a pattern number. Both directions work with the index: forward conversion translates it into an XM order position (taking into account patterns split because of the row limit), backward conversion takes the XM restart position.

### Notes, instruments, volume

**5. XM instrument headers are read using the sizes from the file itself.** The original (`BeRoXM.pas`, `LoadInstruments`) read the extended header as a fixed 214 bytes and sample headers as a fixed 40 bytes, ignoring the `isize` and sample header size fields — on files with non-standard headers everything after the first such instrument was read shifted and turned into garbage. Here the boundaries are taken from the file, with a safety seek to the declared positions.

**6. Instrument names are always ≤ 8 characters:** when looking up in a WAD the engine compares only the first 8 bytes of a name, the rest is silently discarded. Scheme: 6 characters from the sample name + a 2-character slot suffix in base 36 (the original used decimal, which broke at 100+ instruments); plus a check of the output folder so that `.DMI` files of different tracks with the same name do not overwrite each other.

**7. Volume from the XM volume column:** the valid range of the raw byte is 0x10–0x50 (levels 0–64). The `<64` check (as in the dpr) dropped levels 48–63 back to the maximum 127; the top level is also clamped to 127 instead of overflowing to 129.

**8. Volume and channel memory (MOD/S3M/IT/XM).** A note with a sample number and no explicit volume resets the channel to the sample's volume (the ProTracker/S3M rule); a note WITHOUT a sample number and without a volume keeps the channel's current volume (instead of playing at maximum). The channel's last instrument is also remembered between patterns (a note without an instrument number at the start of the next pattern does not become quiet). Checked on `SWAMP2.mod`. An instrument number WITHOUT a note (S3M, MOD) resets the channel's volume to the sample volume without restarting the sound: this is how rhythmic "gating" is done (an instrument number on even rows, volume 8 on odd rows). This reset is written as a volume event (for XM it is done at load time: default volume plus an envelope restart; for IT such a reset is not parsed yet).

**9. The DMM note range is 0..95** (the game's frequency table has 96 entries; byte `0xFE` is a rest, `0xFF` is a volume event, not a note). Out-of-range notes are folded by a whole number of octaves so the table is never read out of bounds.

**10. Encoding like the game data:** a long note is a note with delay=0 (=256 ticks) and one rest for the remainder (the original cut it in chunks of 255 and split rests by 256); an empty channel is not padded with rests to the end of the pattern.

### Samples and IT specifics

**11. Sustain** loops are used (DMM has no note-off, a note is always "held", so the sustain loop takes priority over the normal one). **Ping-pong** loops are unrolled into forward loops (if the unrolled sample fits into 65535 frames, otherwise a forward loop remains, with a warning). **Stereo** samples are mixed down to mono. Samples with a C5Speed above 65535 Hz are decimated (otherwise the value would overflow and play two octaves lower). 16-bit data is rounded, not truncated, when reduced to 8 bits. Channels muted in the tracker are not converted.

**12. In-note volume** — the modes of tab 4 (see above). Inside, the volume trajectory of the sounding note is built from the slides Axy/5xy/6xy/EAx/EBx (MOD/XM), Dxy/Kxy/Lxy (S3M/IT), the XM and IT volume columns and mid-note Cxx settings.

### Game engine limitations

**13.** The engine limits the playback rate of every note to **2000..65535 Hz** (instrument rate × note multiplier; notes that are too high on fast samples "stick" to one frequency — the pitch is lost and a drone is heard). Before writing a `.DMI`, for every instrument the converter picks the maximum safe rate from the notes actually played and compresses the PCM in time by the same ratio: pitch and duration do not change. Small compression ratios use linear interpolation, from 2.5 up a windowed sinc filter (with anti-aliasing). If the note range of one instrument is too wide for a single rate, a warning is logged (separate copies of the instrument are needed). Side effect: in `dmm → xm → dmm` the `.DMI` of several stock Doom2D instruments (whose notes were clamped in the original too) comes out slightly changed; notes and timing do not change.

**14. Format checks:** at most 65535 notes per song (a word in the header), 253 order list entries, 255 patterns and 255 instruments — a clear error is raised when exceeded (it used to crash with `struct.error` or silently truncate data). Samples longer than 65535 frames are decimated.

### Silence at a pattern boundary (`VOLKI-B2.xm`: an instrument cuts off near the end of a pattern)

According to the game's source (`SOUND.ASM`, procedure `playblk`), the engine clears the "sounding voice" (`irate`) of ALL 8 channels EVERY TIME it moves to a new pattern in the play list — even if nothing at all is recorded for that channel in the new pattern. In XM/IT/S3M/MOD a note that nothing has stopped simply keeps sounding across the pattern boundary; in DMM it falls silent unless it is explicitly "re-struck" at the start of the new pattern. If a note is continued with a rest (`0xFE`) across the boundary, the real engine produces exactly the cut-off audible in `VOLKI-B2.xm` (patterns 9→10: a looped instrument started near the end of pattern 9 cuts off at the boundary, whereas in the original it keeps sounding).

**Solution:** for every channel the converter remembers which LOOPED note (not a one-shot — its cut-off at the end of the sample data is expected anyway) is still sounding at the end of a pattern, and if the start of the next pattern does not touch it, it adds the same note/instrument/volume there — an explicit "re-strike" that restores the cleared `irate`. The re-strike sounds like the tail of the original rather than a fresh attack: the envelope clock is shifted by the note's age (RMS average over `[age, age+hold]` in "as before" mode, the envelope tail in `0xFF` events and in the baked sample), and an envelope that has faded to silence carries nothing over. Without this, `BGM12.XM` at the 33→33 boundary would produce a volley of full-volume attacks (85 instead of 53–57) where the original quietly plays out the tails.

If the same pattern appears in the order list several times with different predecessor "tails" (for example `BGM12.XM`: 30, 33, 33 — the first copy of 33 plays out notes from 30, the second plays nothing), copies with different entry states are split into duplicate patterns with new numbers (the first duplicate keeps the native index, the others are appended at the end, and the order list is remapped; the log says "extra pattern slot(s)"). Duplicates are also distinguished by the decayed entry level, so a quiet old tail and a fresh note do not share a slot.

Verified: in `VOLKI-B2.xm` the 9→10 pattern boundary (channels 4 and 6) now gives a correct "re-strike" of the same note instead of a cut-off. The same boundary without an explicit repeat was found in the game's STOCK songs (АС, SUPER and others) — so this is a real, previously unknown defect that affects the original Doom2D music too, not only third-party files. The log prints "Pattern-boundary continuity: re-triggered N note(s) …".

### Volume of a new XM note without an explicit volume command (`BGM16.XM`: 97 % of notes sounded louder than they should)

In FastTracker 2 (and in MOD/S3M/IT) a new note without an explicit volume command (volume column, Cxx) does not sound at maximum but at the instrument's OWN volume from the sample header — many instruments deliberately set it below the maximum to avoid putting Cxx on every note. For XM files this is handled by a separate pass after loading (the instrument's default volume is only known once BOTH patterns AND instruments have been loaded — different XM format versions store them in different order). On `BGM16.XM` this affected 97 % of all notes (the composer relied on the default volume almost everywhere). On MOD/S3M/IT and on XM files where authors set the volume explicitly on every note (like `VOLKI-B2.xm`) it changes nothing.

### Multi-sample XM instruments (`sample_map`)

An XM instrument can hold several different samples and distribute notes among them through a keyboard map (for example, different drum hits on different keys of one instrument), while the whole converter pipeline, like DMM itself, is simpler: one instrument is one sample. Example — `BGM12.XM`: instrument 19 sends ALL notes to its second sample (19 KB of audio, default volume 37), and its sample 0 is empty; instrument 2 splits notes between TWO samples (26 notes of 163 to the first, 137 to the second).

This is handled at XM load time (`_expand_xm_multisample_instruments`): if all the played notes of an instrument land on a single (non-zero) sample, it is simply moved into slot 0 and the instrument number does not change (the instrument 19 case); if the notes spread over several samples, the first used one keeps the same number and every next one gets a new instrument number — as is already done for IT drum kits (the instrument 2 case: 137 notes move to a new, 23rd instrument). Ordinary single-sample instruments (almost all of them) are not affected. This multiplication of numbers raises the instrument count, so the 255 limit check (item 14) counts the multiplied slots.

### Bxx jumps in the middle of a song (`BGM12.XM`/`BGM16.XM`: durations match OpenMPT)

Bxx is tracked everywhere (not only as a backward jump on the last row of the last pattern that defines a restart point):

- the speed/tempo of every pattern is taken from the real playback paths (a simulation from the start, from every jump target, and from the position after a jumping pattern — an Fxx effect inside an unreachable piece does not leak into another song; on a conflict the earliest path wins, and a warning is printed);
- the "split subsongs" checkbox cuts the table into connected songs by OpenMPT's own rules: every order in exactly one song, a song ends before another song's order, at a closed loop (played once) or at the end of the table.

Checked against `openmpt123 --info/--subsong`: `BGM12.XM` gives 4 subsongs of 6:05 / 0:22 / 4:10 / 0:09 versus OpenMPT's 6:04 / 0:21 / 4:09 / 0:08 (the 10:44 total matches), `BGM16.XM` gives 5 subsongs matching to within 0.1 s. Without the checkbox the whole list is converted into one DMM as is, but with the correct speeds. Residual limitation: the DMM restart byte points to a single order position, so a song without an internal loop repeats from its own start, and a return to a pattern with a different "ringing" state than the linear entry is conveyed approximately.

### Forward conversion DMM/WAD → XM

Works by the original algorithm; the changes are dictated by the backward direction and the game's source:

- the XM is created with tempo 165 (`DMM_REF_TEMPO`) and speed = quantization;
- the restart point is translated from a DMM order list index to an XM order position (see item 4);
- the DMM note `0xFF` (the "volume only" event, present for example in СОЛО) becomes an XM cell with just a volume column, not a false note;
- DMM volume 1 does not turn into a "stop" (0x10 in the XM column).

Round-trip check (`dmm → xm → dmm`) on the 30 songs of `doom2d.wad`: with the quantization values from the table of the first tab all notes land on the same ticks for 25 of the 30 songs. For the other five (БОЖ_МУЗ, ПРОБА, ТИШЬ, ТЫ_ПОБЕД, ВЗБУЧКА) the note delays are not multiples of the tabulated quantization; with quantization 1 the timing matches for all 30. The limits of the format itself (64 vs 127 volume steps, ±1–2 Hz in rate, splitting of patterns longer than the row limit) are described above.
